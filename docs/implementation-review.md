**注意**：以上是结构/内容检查，不是对生成模型实际遵循这些规则的证据。Python 静态脚本作为仓库文件交付；可在仓库目录用 `python3 tests/check_static.py` 复查。

## 4. 需要真实模型验证的风险

1. **语义触发**：未显式点名时，模型是否能避免过度激活。
2. **外部引用加载**：目标 Skill 宿主是否按主 SKILL.md 的链接读取 references。不同宿主可能不同；不能凭文件存在断言一定加载。
3. **口癖抑制**：归档里保留“适合万能开场”等历史说明；虽然主规则声明不采纳，也可能受到示例污染。应重点测 T11/T12/T20。
4. **幽默质量主观性**：静态检查无法验证原创自然、有豆味、是否好笑。
5. **提示词 QC 是软约束**：没有真实独立批改 Agent 或自动重试引擎，不能承诺纠错 100% 稳定。
6. **来源真实性**：目前历史语料统一标为未核实，未针对每条热门语录取得可信来源；避免当官方引言。
7. **跨模型一致性**：尚未在目标部署模型上作 A/B，尤其口癖和多轮对话的遵循效果可能不同。

## 5. 进入验收前的建议

- 使用 [20 条用例](../tests/test-cases.json) 对 main 与开发分支同模型同设置对照，保留完整原始输出。
- 优先看 **T03（事实问答）、T06（只改指定角色）、T13（情绪转严肃）、T14（纠错）、T15（禁词/长度）、T16（身份）、T18（锁定内容）、T19（任务切换）**；这些严重失败应阻断合并。
- 对风格问题做最小定向修复，保持旧素材存档，二次执行相同用例集。
- 通过人工 Review 后，再由用户决定是否创建 PR、合并 main。

**当前结论：** 设计 Spec 对应的规则、分类语料库、测试用例已落地；静态契约具备可验证性；真实模型质量未宣称通过。
