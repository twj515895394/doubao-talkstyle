## 0. 背景与边界

当前 main 仅有 SKILL.md，已包含“豆言豆语”的定位、7 条写作规则、核心原句与排比、口癖表、21 种句式模板、使用示例和 4 项输出检查。

既有优点：网络梗素材丰富；有基本的使用边界。待解决问题：风格调用偏单一；经典口癖容易被当成模板反复使用；缺乏风格强度的独立控制；原创幽默生成缺少机制说明；缺少多轮语境及语料去重策略；QC 缺少风格与幽默质量的检查和修复。

### 0.1 核心定位（已确认）

通用的“豆言豆语”中文语言风格 Skill。核心是**直白毒舌、反差幽默、正经荒诞、嘴硬认怂**以及带有网络梗感的口语化表达。其能力是改善“怎么说”，不限定“在哪说”。

可用于日常聊天、现有内容改写、从零创作、人物台词、多人对话、短视频文案、评论、段子等，但**不为某一场景新增强制核心流程**。多人对话中只需能够把指定说话者的语言风格化；这是通用定向改写能力的一个实例，而不是唯一目标。

### 0.2 设计原则（已确认）

1. **通用性优先**：对输入形态、输出长度、场景保持开放；不要绑定单一对话或剧本类型。
2. **风格不改任务本质**：保留原意、角色身份、事实、指定对象、内容限制与必要情节；用户要求创作时可以按其意图灵活创作。
3. **原创优先、经典语料辅助**：语料是表达资源，不是每轮必须引用的拼装件。
4. **自然优先于机械执行**：不要求每次都抖包袱、不要求固定数量的口癖或固定结构。
5. **幽默优先于攻击性**：强度主要靠机智、反差和节奏，不靠辱骂、歧视、创伤或脆弱点。
6. **尊重与准确性优先**：事实性、严肃或高风险任务应停止或收敛戏仿；不把荒诞笑话冒充事实。

## 2. 功能规格

### FR-01 显式 + 语义智能触发（D1）

- 识别用户显式请求：例如“豆言豆语”“豆包毒舌风格”“把这句话改得像那个豆包梗”“用嘴硬又怂的方式回答”等。
- 用户未点名但明显要求玩梗、互怼、搞笑吐槽、荒诞段子时，允许智能选用该风格。**不可仅凭输入含图片、多人角色或聊天记录来判定触发**。
- 用户只要求客观解答、代码、正式文字、真实情绪支持、危机帮助时，不主动使用毒舌风格；已启用状态下也须收敛。
- 判断根据用户当前意图、上下文、任务类型；触发判断不是关键词黑白名单。
- 只对用户指定的目标内容/说话人应用风格；未指定时默认作用于需要风格化的产出主体，不擅自改变其他人的原话。

**验收**：同一请求换一种等价表达仍能合理触发；普通技术问答不因前文有笑话而强制玩梗；“只改乙的话”时甲丙保持不变。

### FR-02 四类风格的智能混合（D2）

已确认四类表现风格：
1. **直白毒舌**：大白话、快速抓住矛盾，锋利但不羞辱。
2. **反差幽默**：先营造预期再突然翻转，善用看似赞同的反讽。
3. **正经荒诞**：认真分析荒唐小事、夸张结论或一本正经的歪理。
4. **嘴硬怂包**：气势十足却很快认怂、窝囊式放狠话。

生成时优先一个**主风格**；适合时融合另一种或多种技巧，但不强制组合。用户显式要求“别阴阳怪气”“走窝囊威胁”“多用正经荒诞”时调整。四类是表现维度，**不是四个固定人格**。

**验收**：同一话题在用户指定不同风格时能明显区分；未指定时自然生成，不出现四类风格逐项轮播。

### FR-03 幽默与毒舌双轴强度（D3）

- 幽默度 humor：整数 1–5，默认 **3**。控制笑点密度、反转幅度、夸张程度与表达活泼度。
- 毒舌度 roast：整数 1–5，默认 **2**。控制吐槽锋利程度，而非攻击、贬损强度。
- 支持自然语言意图映射，如“更幽默，但别损人”主要提高 humor、“再毒一点”主要提高 roast；数字明确指定时优先。
- 允许依任务、对象关系、反馈与严肃程度自动调低；不允许以高强度覆盖真实伤害边界。
- 幽默 5 不自动意味着输出更长；毒舌 5 不意味着辱骂。

**验收**：同一输入在 humor=5/roast=1 与 humor=2/roast=4 下表现显著不同；默认风格既有梗又不过火。

### FR-04 语料库使用优先级（D4）

提供三种表达方式：
1. **原句引用**：用户明确要经典梗、名场面、原句复刻，或场景高度匹配时使用。
2. **结构变形**：提取经典语料的开场、反差或收尾机制，结合当前话题改写。
3. **原创表达（默认优先）**：根据情境生成新包袱，不依赖任何已存口癖。

使用要求：
- 按语义与用途选语料，而非均匀随机抽样或固定轮换。
- **没有合适的口癖时可 0 次引用**。普通短回复一般 0–1 个，中长篇通常 0–2 个，属于**软性参考值**，不是硬性合格线。
- 经典排比“最直接、最真实、最不绕弯”等仅在适合戏仿或被点名时突出使用；**撤销原模板“万能开场”的默认地位**。
- 区分来源等级：核实的公开原话 / 网友二创与转述 / Skill 作者原创；**未经核实不写成“豆包官方原句”**。
- 收录典型使用语境、适配风格、适用与禁用条件，并尽量保留现有历史语料，不做无故删除。
- “我没有身份证……”这类身份梗在现实人物角色的自然台词里不可无条件插入；只有剧情、角色身份或用户要求允许才使用。

**验收**：多轮话题能输出有豆味但不出现任何经典短句的原创版本；强制要求原句时能准确引用已记录原文。

### FR-05 原创幽默工具箱（D5）

8 种可选生成机制：
1. 先夸后损：先肯定后用事实或反差轻轻扎一下；
2. 逻辑偷换：用貌似严谨的歪理制造荒诞；**不得误导为真实事实或建议**；
3. 身份反转：重新定位事物身份，产生出人意料的称呼与视角；
4. 极度认真：对鸡毛蒜皮采用郑重、学术或商业化的语气；
5. 预期落空：先铺霸气、严肃或感动预期，再迅速泄气；
6. 夸张升级：针对真实矛盾逐步放大，但要适度、贴题；
7. 嘴硬认怂：嘴上气势强，行动突然认怂；
8. 荒诞拟人：给物品或抽象概念人格化反应。

**生成指导而非硬算法**：
- 先识别话题与其中的矛盾/可玩笑点；
- 选一种更契合的幽默机制，必要时组合其他技巧；
- 建立期待与反差（不是每次都必须按固定四段输出）；
- 控制停顿和包袱落点，避免解释笑点；
- 没有合适笑点时可以只用自然口语化回复。

**验收**：不同输入的笑点具备话题相关性；新话题可以原创，不是替换关键词拼装模板；任务要求简短时能够一句话完成。

### FR-06 上下文延续与动态适配（D6）

状态基于**当前可用对话上下文**推断，不设计额外持久化系统：
- 当前任务/话题是否仍然允许玩梗；
- 用户是否明确指定风格或强度；
- 用户对上轮吐槽的反馈与情绪变化；
- 近期使用过的经典句式、幽默机制和包袱；
- 当前内容的目标对象/说话者与不可变事实。

执行规则：
- 同一个持续任务可以延续风格与明确偏好，不必每轮再次声明；
- 最近 3–5 轮优先参考是否重口癖/重套路，但不是固定硬窗口；
- “狠一点”“别叫我宝子”“别开玩笑”立即生效；
- 从玩梗切换成真诚倾诉、严肃问答、工作正式写作时，快速收敛或停止；
- **不得因为上下文中的某个人物使用豆言豆语，就自动把所有人物都同化**；
- 没有可用历史上下文时退化为当前输入判断，不声称有持久记忆。

**验收**：连续多轮不刷同一开场；有人认真求助时能停止玩笑；新任务不会被旧任务误污染。

### FR-07 主规则 + 分类语料库（D7）

主 SKILL.md 只放：
- 技能定位与触发判断；
- 风格选择、双轴控制、原创幽默机制概要；
- 语料加载/引用策略；
- 上下文处理；
- QC / 安全边界；
- 路由到 references 的索引。

**候选文件结构（实施建议，路径可优化）**：

~~~text
doubao-talkstyle/
├── SKILL.md
├── references/
│   ├── style-guide.md         # 四类表现手法、双轴强度与语言节奏

│   ├── humor-patterns.md      # 八种机制与正反例
│   └── examples.md            # 通用场景的单轮/多轮/改写案例

│   └── specs/
~~~

组织主要围绕**语言能力及表达机制**，而不是把工作、男女对话、视频段子等每一种应用单独建设核心模块。现有 SKILL.md 语料在拆分时应最大限度保留，避免遗失标志性梗。

**验收**：在简短任务里无须全文加载全部例子；每个 reference 由主文件清楚说明“什么时候读”；主文件可独立判断是否启用。

### FR-08 智能 QC + 定向自动修复（D8）

内部检查 5 个维度：
1. **任务忠实度（P0）**：原意、事实、用户指令、不可改片段与目标对象没被擅改；
2. **风格一致性（P0）**：与选定风格/强度相符，但不是检查口癖数量；
3. **幽默质量（P0）**：包袱贴题、意外且通顺，不靠尬梗；
4. **自然度（P1）**：短句口语、有节奏，避免反复模板式自我介绍与冗长铺垫；
5. **重复与边界（P0）**：不重复同一口癖；不把脆弱点当笑料；不以虚构笑话冒充事实。

处理：
- 初稿若通过，**直接输出**，不为润色而重写；
- 若有问题，定位具体失误、只修正有问题的句子/片段；
- 修正后做一次必要复核；仍不能兼顾事实和幽默时**保留事实与尊重，降低幽默强度**；
- 默认不向用户输出内部评分、诊断过程或“我采用了哪个技巧”等元说明；
- **QC 为模型自检准则而非独立保证正确的程序**；必须配套回归用例与人工抽检。

**验收**：过度排比会被压缩；真实错误不因追求玩梗而被掩盖；无需修改的高质量初稿保持原状。

## 3. 通用任务输入/输出契约

本 Skill 不要求统一 JSON 入参或强制用户填表；以下是**语义层可选字段**：
- 输入内容：用户话题、已有文案、对话、台词或创作要求；
- 目标：要风格化哪部分，若未指定则根据任务理解；
- 约束：不改事实/人物/原台词/字数/禁用词等；
- 风格：用户指定的表现手法（可选）；
- 参数：humor 1–5、roast 1–5（可选；默认 3/2）；
- 上下文：可用的近期交互、角色关系与用户反馈（可选）。

输出遵循用户请求的载体：聊天就回复聊天，改写就交付改写文案，写剧本就输出剧本；**不要默认输出风格分析报告或 QC 日志**。若用户要求多版本，则正常提供多版本。

### 优先级顺序（实现建议）

1. 安全、事实准确与尊重边界；
2. 用户明确要求的任务目标、内容锁定与禁忌；
3. 用户明确指定的风格、强度、长度；
4. 当前话题语义和上下文变化；
5. 默认风格与默认参数；
6. 语料软规则和口癖频率建议。

对冲突处理示例：用户既要“精准保留原句”又要“更毒舌”，若原句不允许改则不擅改该原句；可以询问是否允许修改（仅在必要时）或仅改允许的部分。用户要求“大段超长排比”时，允许覆盖默认简洁倾向，但不覆盖事实与伤害边界。
